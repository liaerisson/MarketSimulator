The order book types seem to be really critical to maintaining it's function.
  * BUY/SELL designations need to be separated from specific "turn" actions
  * price is a 64-bit int so that cents can be included without creating weird calculation issues that occur with doubles
  * quantity MUST be positive, so an unsigned int is the way

Constructor Initializer lists can initialize fields when the object is made
  * apparently this is used to have const fields
  * it's also good for performance
    
    Order(int orderId, int traerId, ...) 
        : orderId(orderId), traderId(traderId), ... 
        { 
            constructor part 
        }

Using unsigned ints gives some validation about the content of the fields --> they are not negative

order books need to decide who gets to buy/sell their orders first
  * this needs a way to prioritize certain traders, so a queue
  * higher price = earlier buys, earlier time (for same price) > later time

  maps are sorted in C++, and then a queue is good for picking between traders who said the same price
    --> there are unordered maps that store the relations without sorting them
    --> lookups in map of O(log n) complexity, so they should be reduced if possible
  iterators! --> these seem to be able to "auto" loop through lists and hold a pointer to their beginning point

Enums
  * to use enums in an if statement:
        if(side == Side::BUY) {}
lists
  * to add an item to the list, use push_front() for the start and push_back() for the end

the iterator value has to hold the location of the current last value in the array (the newest order!). end() gets us to one after the last element, so "deincrementing" is needed.
                auto it = buys[price].end();
                --it;
                location.iterator = it;

                OR

                location.iterator = std::prev(buys[price].end());

auto it = orderLookup.find(orderId) --> a single map entry, with a pair of values

.h files --> headers
  * headers exist to allow for cross-file access to classes, fields, and methods
  * they include full structs and enums, and declarations of classes and their methods without full implementation

Order books have a "best sell"
  - limit price = worst price to pay
  - execution price = price that is actually paid (price wanted by seller)

After looking into order book rules
  - Sell: $100, Buy: $103 --> the $100 is the price
  - Sell: $100, $102, Buy: $103 --> the $100 is still the price
This also depends on the units, but the lower-priced sell price is filled first before going up to the maximum accepted price by the buyer
  - Sell: $100, $103, Buy: $104 --> the $100 is the sell price

Handling matches
  --> it seems really redundant to check all the possible matches regularly
  --> checking each new order against the currently-existing orders seems like the way
